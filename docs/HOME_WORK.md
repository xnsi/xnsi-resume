# ДЗ 1 — От технического задания к опубликованной персональной странице

## Цель

Самостоятельно пройти полный цикл небольшой продуктовой итерации:

1. сформулировать требование;
2. изменить сайт в соответствии с ним;
3. проверить результат;
4. зафиксировать работу в Git;
5. опубликовать итоговую версию.

В этой работе оценивается не количество текста и не сложность дизайна, а согласованность `docs/TECH_TASK.md` и работающей страницы.

## Срок

До ВС (13.09.2026) до 10:00 мск

## Формат работы

Задание выполняется индивидуально.

В результате нужно отправить две ссылки:

- на основной merged pull request с домашней работой;
- на опубликованный сайт в GitHub Pages.

Если итоговый чек-лист заполнялся отдельным pull request, приложите также ссылку на него.

## Важные ограничения

- Работайте в собственном fork, а не в репозитории преподавателя.
- Все содержательные изменения ТЗ и сайта должны находиться в одной рабочей ветке и одном основном pull request.
- Единственное допустимое исключение: заполнение итогового чек-листа можно вынести в отдельный pull request.
- Pull request должен быть направлен в `master` вашего собственного fork.
- Внутри одного pull request можно и нужно сделать несколько логических commits.
- К моменту сдачи все созданные в рамках ДЗ pull requests должны иметь статус **Merged**. Открытый или просто закрытый без merge pull request не считается сданным.
- Не придумывайте опыт, проекты, достижения и навыки. Учебный или незавершенный проект подходит.
- Публикуйте только те персональные данные, которые готовы оставить в открытом доступе. Телефон, домашний адрес и личная почта не требуются.
- Основная часть выполняется на готовой HTML/CSS-структуре без JavaScript.

## Шаг 0. Подготовьте собственный проект

1. Сделайте fork репозитория с заданием.
2. Убедитесь, что владельцем fork является ваш GitHub-аккаунт.
3. Переименуйте репозиторий в `<YOUR_GITHUB_LOGIN>.github.io`.
4. Если репозиторий с таким именем у вас уже существует, используйте имя `<YOUR_GITHUB_LOGIN>-resume` и настройте для него GitHub Pages.
5. Клонируйте именно свой fork и откройте его в VS Code.
6. Включите GitHub Pages по инструкции из репозитория.
7. Создайте ветку `homework-1` от актуальной ветки `master`.
8. Откройте `docs/TECH_TASK.md`, `index.html` и страницу в браузере.

Проверка: адрес клонированного репозитория содержит ваш GitHub-login, а стартовая страница открывается локально.

## Правило выполнения каждого этапа

На каждом этапе соблюдайте один порядок:

1. сначала дополните соответствующий раздел `docs/TECH_TASK.md`;
2. затем измените связанный блок в `index.html`;
3. обновите страницу в браузере;
4. проверьте записанный критерий готовности;
5. исправьте противоречия между ТЗ и страницей;
6. сделайте логический commit.

Не заполняйте все ТЗ задним числом после готовой реализации.

## Этап 1. Позиционирование и первый экран

В `docs/TECH_TASK.md` укажите:

- одну основную аудиторию страницы;
- цель страницы: что посетитель должен понять или сделать;
- одну пользовательскую историю в формате «Как ..., я хочу ..., чтобы ...»;
- проверяемый критерий готовности hero.

После этого обновите hero на странице:

- укажите свое имя и профессиональную роль или направление развития;
- напишите короткое описание, в котором есть один hard skill, один soft skill и один результат либо учебная цель;
- оставьте только релевантные теги навыков;
- проверьте текст и адрес основной ссылки или кнопки.

Проверка: по первому экрану представитель выбранной аудитории понимает, кто вы, чем занимаетесь и куда перейти дальше.

## Этап 2. Доказательство опыта

В `docs/TECH_TASK.md` укажите:

- что именно страница должна доказать посетителю;
- какой блок используется как доказательство: опыт работы или проект;
- наблюдаемый критерий готовности этого блока.

После этого обновите минимум одну карточку опыта или проекта:

- назовите реальную задачу;
- опишите свой вклад;
- укажите полученный результат или честное текущее состояние;
- добавьте работающую ссылку, если результат опубликован.

Если коммерческого опыта нет, используйте учебный, личный или незавершенный проект. Не придумывайте место работы и результаты.

Проверка: карточка подтверждает обещание из hero, а не существует отдельно от позиционирования.

## Этап 3. Навыки и уровни

В `docs/TECH_TASK.md` опишите своими словами:

- что для вас означает опытный уровень;
- что означает средний уровень;
- что означает базовый уровень.

После этого обновите блок навыков:

- укажите минимум один реальный навык в каждой группе;
- удалите навыки, которыми фактически не владеете;
- распределяйте навыки по тому, что можете сделать и объяснить, а не по желаемому впечатлению.

Проверка: вы можете привести пример работы для каждого уровня и объяснить, почему отнесли навык к этой группе.

## Этап 4. Образование и контакт

В `docs/TECH_TASK.md` укажите:

- какое образование важно показать;
- какое действие должен выполнить посетитель после просмотра страницы;
- критерий готовности блока.

После этого:

- замените моковые данные об образовании;
- добавьте минимум один реальный публичный способ связи;
- удалите неиспользуемые моковые контакты;
- проверьте ссылку кликом.

Проверка: сведения корректны, а минимум один безопасный контакт открывается по клику.

## Этап 5. Границы и итоговая проверка

Заполните в `docs/TECH_TASK.md`:

- одно техническое или содержательное ограничение;
- один пункт, который сознательно не входит в первую версию;
- один открытый вопрос для будущей итерации.

Затем проверьте весь проект:

- на странице не осталось ФИО Иванова Иван Ивановича и другой ложной моковой информации;
- `docs/TECH_TASK.md` и `index.html` не противоречат друг другу;
- каждый критерий из ТЗ можно проверить на странице;
- все ссылки открываются и ведут туда, куда обещают;
- страница читается на широком экране и на ширине около 360 px;
- в консоли браузера нет ошибок, вызванных вашими изменениями;
- итоговая версия открывается через GitHub Pages.

## Сдача

1. Отправьте все commits ветки `homework-1` на GitHub.
2. Создайте один pull request из `homework-1` в `master` собственного fork.
3. В описании pull request укажите:
   - основную аудиторию и цель страницы;
   - какие этапы выполнены;
   - как проверить опубликованный результат;
   - что осталось за границами первой версии;
   - использовали ли вы AI и для чего именно. Если не использовали, так и напишите.
4. В самом файле `docs/HOME_WORK.md` заполните итоговый чек-лист: замените `[ ]` на `[x]` у каждого действительно выполненного пункта.
5. Заполненный чек-лист можно включить в основной pull request или оформить отдельным pull request после основной работы.
6. Выполните merge основного pull request и отдельного pull request с чек-листом, если он создавался.
7. Убедитесь, что к моменту сдачи в репозитории не осталось незамерженных pull requests, созданных в рамках ДЗ.
8. Дождитесь публикации итоговой версии из `master`.
9. Отправьте преподавателю ссылку на основной merged pull request, ссылку на GitHub Pages и ссылку на merged pull request с чек-листом, если он был отдельным.

## Оценивание основной части — до 8 баллов

### 1. Репозиторий, публикация и формат сдачи — до 1 балла

- используется собственный fork;
- сайт опубликован через GitHub Pages;
- содержательная работа собрана в одном основном pull request в `master` собственного fork;
- все pull requests по ДЗ замержены;
- приложены ссылки на PR и сайт.

### 2. Этап 1: позиционирование и hero — до 1,5 балла

- аудитория, цель, user story и критерий связаны между собой;
- hero соответствует им и содержит честную персональную информацию;
- критерий сформулирован так, что его можно проверить на странице.

### 3. Этап 2: опыт или проект — до 1,5 балла

- в ТЗ понятно, что нужно доказать посетителю;
- карточка содержит задачу, вклад и результат либо текущее состояние;
- карточка поддерживает позиционирование из hero.

### 4. Этап 3: навыки — до 1,5 балла

- уровни описаны через реальную самостоятельность студента;
- в каждой группе есть минимум один навык;
- моковые и недостоверные навыки удалены.

### 5. Этап 4: образование и контакт — до 1 балла

- данные об образовании актуализированы;
- указан минимум один безопасный публичный контакт;
- контактная ссылка работает.

### 6. Границы и согласованность — до 0,5 балла

- указаны ограничение, граница первой версии и открытый вопрос;
- ТЗ и реализация не противоречат друг другу.

### 7. Проверка и качество сдачи — до 1 балла

- на странице не осталось заведомо ложной моковой информации;
- страница не сломана на desktop и ширине около 360 px;
- commits и описание PR позволяют понять ход работы;
- студент может объяснить внесенные изменения.

## Бонус — до 2 баллов

Бонус не заменяет обязательную часть и оценивается только при работающей базовой версии.

### +1 балл. Собственная стилистика

Измените `styles.css` и создайте целостное оформление страницы: собственные цвета, типографику, интервалы и состояния интерактивных элементов. Сохраните читаемость, видимые границы блоков и базовую адаптивность. Простая замена одного цвета бонусом не считается.

### +1 балл. Содержательное расширение

Добавьте один новый полезный раздел, которого нет в базовом шаблоне: например, достижения, направления интересов, языки, сертификаты или подробный кейс проекта.

Для бонуса необходимо:

- сначала добавить назначение и критерий раздела в `docs/TECH_TASK.md`;
- реализовать раздел семантической HTML-разметкой;
- привести его к общей стилистике;
- проверить на desktop и ширине около 360 px.

Простое дублирование существующей карточки без нового содержания и требования бонусом не считается.

## Штрафы и основания для 0 баллов

Следующие правила относятся ко всей работе, включая основную и бонусную части:

- **Домашнее задание не сдано до дедлайна — 0 баллов.** Работа должна быть полностью опубликована и отправлена до ВС (13.09.2026) 10:00 мск. Создание репозитория, commit или pull request после дедлайна не считается своевременной сдачей.
- **При обнаружении признаков чужого кода, чужого текста или результата, сгенерированного нейросетью, — 0 баллов.** Нельзя копировать работу другого студента, готовое решение из интернета или переносить в сдаваемую работу ответ AI как собственный результат.
- **При невозможности ответить на вопросы по своему ТЗ или коду — 0 баллов.** Преподаватель может попросить объяснить любое требование, HTML/CSS-фрагмент, изменение, commit или решение из pull request.
- **При незаполненном итоговом чек-листе — 0 баллов.** Каждый пункт чек-листа в `docs/HOME_WORK.md` должен быть осознанно проверен и отмечен `[x]`. Наличие хотя бы одного пункта `[ ]` означает, что работа не готова к сдаче.
- **Если к моменту сдачи остался незамерженный pull request по ДЗ — работа считается не сданной и получает 0 баллов.** Статус Closed без merge не подходит.

Частично выполненная собственная работа оценивается по критериям выше. Самостоятельность и понимание важнее формального наличия всех пунктов.

## Использование AI

AI разрешено использовать только как консультанта, но не как автора сдаваемой работы. Допустимо:

- попросить задать уточняющие вопросы;
- проверить требование на неоднозначность;
- предложить варианты короткой формулировки;
- помочь найти причину технической ошибки;
- провести самопроверку по критериям.

Полученные подсказки нужно самостоятельно проверить, осмыслить и сформулировать своим языком. Нельзя просить AI выполнить все ДЗ, генерировать готовые `docs/TECH_TASK.md`, `index.html` или `styles.css`, а также копировать его ответ в сдаваемую работу.

Нельзя оставлять в работе выдуманные AI факты или код, который вы не понимаете. Ответ AI — предложение, а не подтвержденное требование. За каждую итоговую формулировку и строку кода отвечает автор работы.
